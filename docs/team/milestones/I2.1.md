## Decisions and implementation

- File import accepts exactly the activity's case-sensitive `entryClassName.java` basename. It bounds file bytes to 100,003 before reading, decodes UTF-8 strictly, accepts/removes a UTF-8 BOM, rejects blank/null-byte content, enforces 100,000 UTF-16 code units and checks normalized UTF-8 source against the standard backend's 100,000-byte limit. A larger multibyte file was previously accepted by import but rejected by Run/Submit; this mismatch is corrected and regression-tested. Server validation remains authoritative.
- A conservative precheck requires one ordinary public top-level class with the expected name and no package declaration. Comments, string literals and nested classes cannot stand in for the entry class. This is not a full Java parser; javac remains authoritative. Unusual annotations/Unicode-escaped declaration syntax may need ordinary spelling or direct editor input.
- Import asks before replacing any non-empty source, including starter code. Invalid files/cancellation preserve source; a read finishing after editor unmount is ignored. Import clears the file input and does not call APIs or persist source/local paths.
- The textarea retains horizontal scrolling without soft wrap, synchronized line numbers and four-column indentation guides, Tab/Shift+Tab block editing, and Enter indentation. Escape then Tab allows keyboard exit. IME composition and modifier shortcuts are not intercepted.
- Bounded `EntryClass.java:line:` compiler references focus/select the matching line. Other files, paths, invalid/out-of-range lines are not linked. Links disappear if source differs from the last run snapshot; compiler output remains plain text.
- The synthetic checkout reference uses `AlingNenaStore`, proving activity-specific naming. Packaged source compiles but fails at the current unqualified launch contract. No runner change was needed.
- Adaptations specify stdin separately from stdout, exact labels/spacing/precision and valid domains. The checkout cash ambiguity and quadratic sample/starter mismatch are recorded. Fixed-value exercises remain fixed-value exercises; calling-card output remains personalized and its new checking policy is pending, not published as a fixed synthetic answer.

### Instructor review rerun reassessment

Persistent review-run records are not a logical requirement of an ungraded rerun. Reusing `createJavaRunner` is possible and its time/output/heap/cleanup controls should remain unchanged. However, the existing separate worker dispatches only `OFFICIAL_ASSESSMENT` and `VISIBLE_TEST_RUN`. Each ExecutionJob has an exclusive unique submission/practice target, reinforced by `execution_jobs_target_check`; official completion writes original assessment evidence, while practice creation requires a Student and applies Student membership/activity/deadline/concurrency rules. Retrying an assessment or attributing Instructor work as Student practice does not meet the requested behavior.

A migration-free, transient Instructor task is technically possible, but requires a separately approved API-to-worker dispatch/lifecycle design with global concurrency, rate limits, bounded input/results, cancellation semantics, authorization and safe audit attribution. It is not an existing configuration toggle or a safe same-day substitution for the durable queue. Extending the current durable queue with an isolated review target/job kind is the smallest architecture-consistent proposal; that needs a bounded non-destructive schema/migration approval. Neither option was implemented. The personalized calling-card comparison mode also remains deferred, not replaced with exact fictional output. Today's deterministic demo does not depend on either extension.
