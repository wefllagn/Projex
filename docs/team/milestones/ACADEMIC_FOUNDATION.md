Protected-branch integration remains separate.

## Delivered behavior

- Admin manages reusable Course Number/Name records and can preview, validate and atomically confirm bounded Course CSV imports. Course edits leave each Class's stored Course Number/Name snapshot unchanged.
- The existing Class UUID remains the relationship identity. Additive nullable fields distinguish official Class Code, Course, Academic Period, School Year, schedule, days and room from the generated private join code. Neither Course nor Official Class Code is constrained to a semester, and Official Class Code is not globally unique.
- Instructor informal Class creation remains supported. Admin can create an official Class with an active Primary, or a PREPARED offering without one. Admin can verify/correct an existing Class in place after reviewing history counts, acknowledging existing history, providing a reason and matching its version; the Admin audit event records before/after identity. This preserves the same Class UUID and related academic records.
- Primary Instructor, accepted Co-Instructors and Admin have separate roles. A Co invitation gives no access until accepted. Active Co-Instructors share Student roster/invitation and academic review/rerun access, but cannot invite/remove teaching staff or transfer Primary. The Primary may transfer to an active Co and explicitly remain as Co or leave. Admin may assign/recover an ACTIVE Primary with an explicit former-Primary disposition and reason. ACTIVE Classes require a Primary; PREPARED Classes have an inactive join code. Deactivation of an account still serving as Primary for an ACTIVE Class is blocked.
- Admin or authorized teaching staff may preview and atomically confirm bounded CSV invitations for registered ACTIVE Students. Confirmation creates pending invitations, never direct membership; acceptance remains the Student's action.
- Affected class, activity, submission, repository, project-task, Git transport and Admin projections use the teaching-staff policy. The frontend exposes Course, offering, staff and invitation controls while keeping official correction Admin-only.

## Migration and data boundary

The additive migrations `20260930000000_course_class_teaching_foundation` and `20260930000100_course_class_teaching_tables` were deployed in order to the independently verified disposable `projex_test` database only. They are split because PostgreSQL cannot use a newly added enum value in the same migration transaction. Legacy Class rows remain compatible; no migration rewrites Class UUIDs or dependent records. The normal local `projex` database was **not** migrated or modified. Its migration requires separate approval before a normal-local walkthrough.
