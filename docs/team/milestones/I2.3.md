## Implemented behavior

- `GET /api/v1/repositories/:repositoryId/activity` returns a bounded, paginated projection of system `REPOSITORY_PROVISIONED` and authenticated user `PUSH` records only. It omits raw event metadata and counts accepted pushes by authenticated Projex user across the repository, independent of the current event page.
- The Student and owning Instructor repository detail displays recorded events and per-user accepted-push counts. It explicitly distinguishes these operation counts from Git commit authorship and code-contribution percentages.
- Manual refresh is ordered so an older response cannot overwrite a newer result. A focused test covers the overlap.
- The repository reader resolves the root tree of a selected commit as a Git tree object. A real-Git regression covers explicit commit and default-branch root views.
- No endpoint infers a push from Git commit author strings or adds event types that the current service does not record authoritatively.

## Controlled localhost walkthrough

- Reused private local Admin, Instructor, and Student accounts and an existing ACTIVE class. The Instructor created one draft project task through the authenticated API because the browser automation did not commit the native date-time input, then published it through the UI.
- The Student saw the published task, created a team and class-project repository, and the process-only loopback Git worker provisioned it. The activity panel initially showed no event before the asynchronous worker finished; Refresh then showed one system provisioning event.
- With repository review transitions, the Student marked it ready, the Instructor requested changes with released feedback, the Student saw that feedback and resubmitted. A second request-changes cycle allowed one native-Git `main` push using a short-lived repository-scoped credential. The credential was revoked and the disposable local Git clone was removed after the push.
- The Git commit used a deliberately different, self-asserted author label. The activity feed still showed the authenticated Student as the push actor and exactly one accepted push; it did not display the author label as verified identity. The Student resubmitted, the Instructor approved, then archived and restored the repository. Both recorded events and the count remained visible.
- The first post-push root file-tree read returned 404 because the pre-existing reader checked the commit object as a tree. After the focused correction and guarded real-Git regression, the owning Instructor reopened the repository and saw the root `README.md` plus its authorized text preview.
- Admin authenticated API access returned both events and one accepted-push count; unauthenticated access returned 401. Student and owning Instructor views displayed the same bounded evidence. Cross-owner, outsider, classmate, and removed-member denials passed guarded integration tests; no second controlled classmate account was available for manual invitation acceptance.
- The Student repository page and activity panel were visually checked at 1280 px and 390 px. At 390 px the document width stayed within the viewport, and event rows/counts remained readable. The owning Instructor was checked on desktop. A separate Instructor narrow-screen pass and VS Code-specific client pass were not performed.

## Security, effects, and limitations

- Authorization is enforced in the service after ACTIVE-user and repository access checks. Raw metadata, credentials, managed Git paths, and Git source are absent from the new activity projection. A `CLASS_ONLY` repository's metadata may remain visible to an eligible classmate, but its activity feed returns 404 unless that classmate is an active repository participant.
- No source code, test database, schema, migration, dependency, tracked environment file, or persistent worker/network setting was changed by the manual walkthrough. The normal local `projex` gained only controlled project/task, team/repository, review/feedback, Git credential metadata, and event records through supported authenticated flows; no normal-database migration was applied for this slice.
- The root file-tree defect was present at baseline HEAD and is fixed in this directly related repository-workflow slice. No unrelated storage or restore implementation was changed.
- Existing classmate selection offered no invitee because the controlled class had only one Student. Invitation acceptance and member transitions have guarded integration evidence, not a complete manual two-Student walkthrough.
- Git Smart HTTP was enabled only for the running built API on loopback. The development launcher could not start with Smart HTTP because its source-tree hook `.js` is absent; the already-built server entry point worked. No persistent configuration was changed.
